# Linux Process States and Signals

## 1. Introduction

Linux manages every running process through the kernel. A process may execute instructions, wait for an event, become stopped, or finish execution.

Linux exposes process state information through tools such as `ps` and `top`. Signals provide a mechanism for notifying processes and requesting actions such as termination, stopping, or resuming execution.

Understanding both concepts helps DevOps engineers troubleshoot applications and manage processes safely.

---

## 2. Linux Process States

The `STAT` column in `ps` displays a process's state. Common state codes include the following.

| State | Meaning | Explanation |
|---|---|---|
| `R` | Running or runnable | Executing on a CPU or ready to run |
| `S` | Interruptible sleep | Waiting for an event and can generally be awakened by a signal |
| `D` | Uninterruptible sleep | Waiting in a kernel operation, commonly related to I/O |
| `T` | Stopped | Suspended, often by job control or a stop signal |
| `t` | Tracing stop | Stopped during tracing or debugging |
| `Z` | Zombie | Has exited but its parent has not yet collected its exit status |
| `I` | Idle kernel thread | An idle kernel thread; typically not an ordinary application process |

Additional letters may appear in `STAT` to indicate properties such as multithreading or session leadership.

### Running and Runnable (`R`)

A process marked `R` is either running on a CPU or ready to run.

Example:

```bash
ps -eo pid,stat,comm
```

A process may appear runnable even when it isn't executing at the exact instant you inspect it.

### Interruptible Sleep (`S`)

A process in state `S` is waiting for an event, such as incoming network data or a timer.

This is normal behavior. A server waiting for a request may spend much of its lifetime in this state.

### Uninterruptible Sleep (`D`)

A process in state `D` is waiting in a kernel operation that generally cannot be interrupted by ordinary signals until the operation reaches an appropriate point.

This often happens during storage or other I/O operations.

If a process remains in `D` for an unusually long time, investigate the underlying I/O, storage, or kernel issue. Sending `SIGKILL` does not immediately remove a process that is stuck in uninterruptible sleep.

### Stopped (`T`)

A stopped process is suspended and isn't executing its normal instructions.

This can happen when a user pauses a foreground job or sends a stop signal.

A stopped process may be resumed using job control or `SIGCONT`.

### Zombie (`Z`)

A zombie is a process that has already exited, but its parent hasn't collected its exit status using a wait operation.

A zombie isn't actively running and doesn't consume CPU like a normal running process. It retains a small process-table entry until it is reaped.

If many zombies accumulate, investigate the parent process and how it handles child-process termination. Killing the already-exited zombie itself won't solve the problem.

## 3. What Are Linux Signals?

A signal is a notification delivered to a process or thread.

Signals can originate from users, the kernel, or other processes. Their purpose varies: some request termination, others stop or resume execution, and some notify applications about events.

Common signals include:

| Signal | Typical number on Linux | Purpose |
|---|---:|---|
| `SIGHUP` | 1 | Hangup notification; some services interpret it as a reload request |
| `SIGINT` | 2 | Interrupt, commonly generated by Ctrl+C in a terminal |
| `SIGKILL` | 9 | Forces process termination |
| `SIGTERM` | 15 | Requests process termination |
| `SIGSTOP` | 19 on common Linux architectures | Stops a process |
| `SIGCONT` | 18 on common Linux architectures | Resumes a stopped process |

Signal numbers can differ across operating systems and architectures. Use signal names when possible.

---

## 4. SIGTERM vs SIGKILL

### SIGTERM

`SIGTERM` asks a process to terminate.

An application can handle this signal to stop accepting new requests, finish or cancel work, close connections, and release resources.

Example:

```bash
kill -TERM 1234
```

Replace `1234` with the target process's PID.

### SIGKILL

`SIGKILL` forces termination. The process cannot catch, block, or ignore this signal, and it doesn't get an opportunity to perform its normal signal-handling cleanup.

Example:

```bash
kill -KILL 1234
```

Use it only when necessary, after investigating why graceful termination isn't working.

**Important:** Neither command guarantees that a process disappears immediately. For example, a process stuck in uninterruptible sleep may remain visible until the kernel operation resolves.

---

## 5. Stop and Resume a Process

You can stop a process temporarily:

```bash
kill -STOP 1234
```

Resume it with:

```bash
kill -CONT 1234
```

`SIGSTOP` and `SIGCONT` are useful for understanding process control, but pausing a production process can interrupt service. Use them cautiously.

---

## 6. Inspect Process States

### Display process states

```bash
ps -eo pid,ppid,stat,comm
```

This displays each process's PID, parent PID, state, and command name.

### Inspect a specific process

```bash
ps -p 1234 -o pid,ppid,stat,comm
```

Replace `1234` with the actual PID.

### Check signal names

```bash
kill -l
```

This lists signal names supported by the system.

---

## 7. DevOps Example

Imagine a service is no longer responding correctly, and you have identified its process.

First, inspect it:

```bash
ps -p 1234 -o pid,ppid,stat,%cpu,%mem,comm
```

If you have confirmed that the process should be stopped and you have permission to manage it, request graceful termination:

```bash
kill -TERM 1234
```

Check whether it has exited:

```bash
ps -p 1234
```

If the process remains, investigate its state and application logs before deciding what to do next. Do not automatically send `SIGKILL` without understanding the consequences.

For a service managed by systemd, prefer investigating and managing the service with `systemctl` rather than killing an arbitrary process directly.

---

## 8. Why This Matters in DevOps

Understanding process states and signals helps with:

- Troubleshooting unresponsive applications.
- Investigating processes with unusually long I/O waits.
- Understanding why a process is consuming CPU or waiting.
- Managing application shutdowns safely.
- Diagnosing zombie processes.
- Understanding how Linux services and containerized applications behave.

## 9. Interview Questions

**Q1. What are the common Linux process states?**

Running or runnable (`R`), interruptible sleep (`S`), uninterruptible sleep (`D`), stopped (`T`), and zombie (`Z`).

**Q2. What is the difference between `SIGTERM` and `SIGKILL`?**

`SIGTERM` requests graceful termination and can be handled by an application. `SIGKILL` forces termination and cannot be caught or ignored.

**Q3. What is a zombie process?**

A process that has exited but whose parent has not yet collected its exit status.

**Q4. Can `SIGKILL` immediately terminate every process?**

No. A process in uninterruptible sleep may remain until the kernel operation resolves.

**Q5. What does the `D` state indicate?**

The process is waiting in an uninterruptible kernel operation, often associated with I/O.

**Q6. How do you inspect a process's state?**

Use `ps -p PID -o pid,stat,comm`, replacing `PID` with the actual process ID.

**Q7. What do `SIGSTOP` and `SIGCONT` do?**

`SIGSTOP` stops a process, while `SIGCONT` resumes a stopped process.

**Q8. How would you safely stop an application process?**

Confirm the correct process, understand its role, request graceful termination with `SIGTERM` if appropriate, and verify the result. For systemd-managed services, use the service manager when appropriate.

## Key Takeaway

Process states explain what a process is doing or waiting for. Signals provide a way to notify and control processes. In production, understand the process and prefer graceful, service-aware operations over forceful termination.
